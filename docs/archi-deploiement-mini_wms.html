Architecture de déploiement · multi-tenant

Le trajet d'une
requête.

Modèle retenu : une app partagée + un schéma Postgres par client. Le tenant est lu dans le JWT Keycloak, résolu par un TenantResolver unique, et Hibernate positionne le bon schéma. Le silo reste l'échappatoire pour un client à isolation forte.

→ trajet de la requête bleu = identité / public app partagée rose = silo (échappatoire)
① → ②L'utilisateur s'authentifie chez Keycloak, qui émet un JWT signé portant le claim tenant. Toute requête vers l'app arrive avec ce token. Le tenant vient de là — jamais d'un header/param/URL.
③Le TenantResolver (frontière unique) lit le claim, le valide contre la liste connue (schéma public) — anti-injection sur le nom de schéma — et rejette (401) si absent. Aucun fallback silencieux.
④Hibernate en mode SCHEMA positionne le schéma courant. Le code métier ne porte aucun filtre tenant : la requête tape physiquement dans acme.*. Un oubli de WHERE est structurellement impossible.
Ajout clientNouveau client = CREATE SCHEMA + Liquibase + realm Keycloak + ligne dans public.tenants. Aucun redéploiement, aucun nouveau conteneur (script add-tenant.sh).
SiloClient à exigence forte → conteneur + base dédiés (provision-client.sh). Même code, même TenantResolver → bascule réversible sans toucher au métier.
